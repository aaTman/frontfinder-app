About this model

Fronts are detected by a convolutional neural network, specifically a UNet 3+ (Huang et al. 2020), trained to predict the probability of a cold, warm, stationary, or occluded front at each grid point. The original method and evaluation are described in the paper published in Artificial Intelligence for the Earth Systems: doi:10.1175/AIES-D-24-0043.1.

The model served here was retrained after that paper was published, with fewer input variables, different pressure levels, and a different loss function than the ones described there. It was trained on data through 2024.

Inputs

Equivalent potential temperature (θe), u-wind, v-wind, and specific humidity, each on six pressure levels (1000, 925, 850, 700, 500, and 300 hPa), for 24 input channels total.

Southern hemisphere

The model is trained only on northern hemisphere fronts, where cyclones rotate counterclockwise. South of the equator the rotation is reversed, so the raw input does not look like anything the model was trained on.

Each forecast is run through the model twice. The first pass uses the grid as published, and its northern hemisphere is what the map shows. The second pass negates v-wind south of the equator and flips the entire grid end to end before inference, then flips the output back; its southern hemisphere is what the map shows there. Flipping the whole grid rather than just the southern half keeps each row's neighboring context intact instead of placing the south pole next to the equator, at the cost of running inference twice per lead time.

Loss function

The model is trained with a neighborhood Brier loss (Roberts and Lean 2008; Stein and Stoop 2024). Instead of scoring each pixel's predicted probability against the exact labeled front location, the target is smoothed over a spatial neighborhood, so a prediction placed close to a front is penalized less than one placed far from any front. This suits a task where even human analysts rarely agree on the exact placement of a front.

The neighborhood Brier loss remains a proper scoring rule (Gneiting and Raftery 2007): a forecaster minimizes their expected loss only by reporting their true belief about the probability of a front in that neighborhood, with no incentive to hedge toward some other value. That property is what lets the model's output be read directly as a probability rather than as an arbitrary confidence score.

Data source

ECMWF IFS HRES (“oper”) forecasts at 0.25° resolution, read directly from the ECMWF Open Data archive on AWS (Amazon Web Services, Registry of Open Data: ECMWF Real-Time Forecasts, s3://ecmwf-forecasts).

Update cadence

A poller checks every 5 minutes for each new IFS forecast cycle (00Z, 06Z, 12Z, 18Z) to start publishing, and runs inference on each lead time as soon as ECMWF has actually published it. Lead times are 6-hourly only: 41 steps out to 240 hours for 00Z/12Z cycles, and 25 steps out to 144 hours for 06Z/18Z cycles. IFS itself publishes some fields every 3 hours out to 144h, but this pipeline deliberately requests only the 6-hourly subset, so the map never shows 3-hourly steps.

Serving

Inference runs on a home server: an Intel Core i7-4770 with 16 GB of DDR3 RAM, no GPU. Each lead time is run as its own tiled inference pass as soon as it becomes available, rather than as one long batch job. A single step's run is capped at a 3-hour timeout as a safety ceiling, well inside the 6-hour gap between IFS cycles.
